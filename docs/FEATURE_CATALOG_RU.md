# Что умеет ArchVerity 6.1.2

Один сервис может попросить у другого платёж, ожидая поле `amount` в ответе. Их договорённость о том, **куда отправлять запрос и какие данные там будут**, называется контрактом. ArchVerity помогает найти оба конца такой связи и проверить, продолжат ли они понимать друг друга после правки.

**Первый раз здесь?** Откройте [маршрут с картинками](VISUAL_GUIDE_RU.md). Этот указатель пригодится, когда вы захотите найти конкретное действие. Названия кнопок даны по-английски, как в IDEA.

| Ваш вопрос | Куда перейти |
| --- | --- |
| «Что сломается от моей правки?» | [Changes](VISUAL_GUIDE_RU.md#changes) |
| «Где именно это видно в коде?» | [Details](VISUAL_GUIDE_RU.md#details) |
| «Кто обращается к этому сервису?» | [Map](VISUAL_GUIDE_RU.md#map) |
| «Что уже расходится в проекте?» | [Problems](VISUAL_GUIDE_RU.md#problems) |
| «Как подключить помощника?» | [Agents](VISUAL_GUIDE_RU.md#agents) |
| «Где проверить запрос, посмотреть SQL или открыть лог?» | [Tools](VISUAL_GUIDE_RU.md#tools) |

Откройте **View → Tool Windows → ArchVerity**. Во всех разделах кнопка с лупой находит нужный экран по названию. Тот же поиск открывается через **Find Action → Find ArchVerity Section…**. Для анализа дождитесь импорта проекта и индексации обоих сервисов. Нужна действующая пробная или платная лицензия. Обычная проверка исходного кода работает локально. AI-помощник для неё необязателен.

**База сравнения** — версия кода, с которой сравнивают ваши файлы. **Клиент** — программа, которая обращается к другой программе за данными. **Профиль Spring** — выбранный набор настроек, например для разработки или для рабочего сервера.

## Проверить одну правку

**Changes → Summary** даёт первый ответ. **Changes → Details** показывает, на чём он основан. [Снимок Summary](VISUAL_GUIDE_RU.md#changes) · [Снимок Details](VISUAL_GUIDE_RU.md#details)

| Что хотите сделать | Куда нажать и что получите |
| --- | --- |
| Попробовать на учебном примере | В **Changes → Summary** выберите **… → Open Demo Project**. При первом запуске также может быть видна кнопка **Try the Demo**. В примере платежи требуют `priority`, а заказы всё ещё посылают прежний запрос. |
| Проверить своё изменение | Выберите **Check Changes**. Плагин сравнит текущие файлы с выбранной версией Git и назовёт затронутые контракты и сервисы. |
| Понять цвет результата | **Breaking** указывает на доказанное несовпадение. **Needs review** просит проверить недостающие сведения. **Compatible** относится к указанной базе и проверенной части проекта. |
| Выбрать точку сравнения | Нажмите строку **Last commit → Current files** и выберите нужную версию. В **Details → Comparison details** видны фактические ревизии и охват. |
| Разобрать длинный список | В **Details** введите имя в поиск или выберите категорию. **Reset filters** вернёт полный список по той же базе. |
| Сравнить несколько репозиториев | Откройте их общую папку и при необходимости укажите базы в `.archflow.yml` через `analysis.repositoryBases`. В **Comparison details** можно увидеть, какая база прочитана для каждого репозитория. |
| Сохранить местную точку отсчёта | В **More actions → Save comparison baseline** сохраните снимок для сравнения. **Clear comparison baseline** убирает эту точку отсчёта. |
| Увидеть, кто зависит от изменения | В **Details** выберите изменённый контракт. В группе под ним видны сервисы, которые его используют, причина и затронутые поля. |
| Открыть оба конца связи | Нажмите **Open Both Sides** для выбранного результата. Можно сверить строку, где сервис посылает данные, со строкой, где другой их читает. |
| Исправить подтверждённую проблему | Если доступно, нажмите **Preview Fix**, прочитайте предложенное изменение и примените его. Затем **Check Again** проверит тот же пример. В учебном проекте можно вручную убрать новое обязательное `priority`. |
| Сохранить решение по отдельному замечанию | **Copy PR note** копирует объяснение для ревью. Если допустили исключение, **Accept with reason…** запишет вашу причину и срок в `.archflow.yml`. |
| Проверить идею ещё до правки | В Java/Kotlin щёлкните правой кнопкой на поддержанном поле, маршруте или отправке/получении Kafka и выберите **ArchVerity: What Breaks If This Changes?**. [Прогноз покажет затронутый вызов](VISUAL_GUIDE_RU.md#what-if) до записи в файл. |
| Найти первый пример в своём коде | Если после анализа появился блок **First steps**, нажмите **What breaks if it changes?** для предложенного контракта. **Copy the Request for Your Agent** скопирует задание с этим примером. |
| Расследовать нечёткий результат | Откройте **Details** и прочитайте причину и следующий шаг. Добавьте названный модуль, профиль, исходник или подтверждение и запустите **Check Again**. |

## Посмотреть связи и уже существующие проблемы

**Map → Analyze Project** читает код открытых модулей. **Problems** показывает расхождения, которые есть уже сейчас, даже если вы ничего не меняли. [Карта](VISUAL_GUIDE_RU.md#map) · [Проблемы](VISUAL_GUIDE_RU.md#problems)

| Что хотите найти | Куда нажать и что получите |
| --- | --- |
| Общую картину | **Map → Graph** показывает сервисы и стрелки между ними. Переключите уровень детализации, чтобы увидеть отдельные маршруты и темы сообщений. |
| Один сервис и его соседей | В **Graph** включите фокус и выберите узел. **Clear focus** возвращает полную карту. Поиск и фильтр протоколов помогают сократить список. |
| Все найденные объекты | В **Map → List** выберите сервис, маршрут или тему. Из выбранного элемента можно открыть его объявление. |
| Одну конкретную связь | В **Map → Links** выберите вызов или сообщение. В карточке видны известные стороны и места в коде. |
| Самые зависимые контракты | После полного анализа откройте **Problems**. Сводка показывает, от каких контрактов зависит больше сервисов и какие связи пока не удалось проследить. |
| Найти проблему в файле | В **Problems** выберите **Breaking**, **Needs review** или **Notes**, затем карточку. В ней есть причина, переход к строке и технические подробности. |
| Найти вызывающие места из редактора | В поддержанном Java/Kotlin объявлении откройте **Find Usages** или нажмите подсказку о потребителях. Инспекции и метки на полях редактора ведут к релевантному результату. |
| Выбрать, что анализировать | В корневом `.archflow.yml` задайте модули, исключения, идентификаторы сервисов и профили Spring. Запустите **Analyze Project** с тем же набором для обеих сторон. |
| Добавить правила своей команды | В `.archflow.yml` задайте разрешённые/запрещённые зависимости, правила и обоснованные исключения. **Problems** покажет найденный запрещённый путь или цикл. |
| Увидеть риск, который легко пропустить | В **Problems → Notes** ищите подмену реального вызова в тестах, скрытую связь, отсутствие тайм-аута или часто меняющийся общий контракт. Запись подсказывает, что проверить. |
| Посмотреть риск перехода на Boot 4 | В **Problems → Check Spring Boot 4 Upgrade** проверьте, где при переходе на новый Jackson один сервис может иначе прочитать данные другого. Есть [учебный проект](../projects/boot-upgrade/README.md). |

## Какие договорённости проверяются

Чтобы увидеть уже существующую связь, начните с **Map**. Чтобы проверить, что изменилось в ней относительно Git, начните с **Changes**. Эти проверки делят экран между собой. [Карта](VISUAL_GUIDE_RU.md#map) · [Kafka](VISUAL_GUIDE_RU.md#kafka) · [База данных](VISUAL_GUIDE_RU.md#database)

| Договорённость | Как её увидеть и что станет понятно |
| --- | --- |
| HTTP между сервисами Spring | В **Map → Links** выберите вызов, затем в **Details** сравните метод, путь, запрос и ответ. Например, отправитель зовёт `POST /payments`, а получатель ждёт `PUT`. [Учебный пример](../projects/first-result/README.md) |
| Форма данных | Измените поле, обязательность или набор допустимых значений в передаваемом объекте и откройте **Details**. Видны затронутые читатели и прежняя и новая формы JSON. |
| Правила приёма данных | После ужесточения проверок запроса, например уменьшения допустимой длины, откройте **Details**. Плагин назовёт клиентов, чьи прежние данные нужно перепроверить. |
| Kafka в Spring Boot | В **Map → Links** найдите отправителя и слушателя. В **Changes → Details** видны тема, группа, форматы записи/чтения и поля старых и новых сообщений, если их удалось определить. [Пример](../projects/kafka-boot-lab/README.md) |
| Повторные попытки и сообщения с ошибкой | На **Map** проследите путь до повторной попытки, темы ошибок или ответа. Выберите активный профиль, чтобы имя темы совпадало с вашей конфигурацией. [Примеры профилей](../projects/kafka-profile-lab/README.md) |
| Что действительно работало в Kafka | В **Map → Kafka → Import…** просмотрите запись нужного запуска, затем **Inspect pair**. Сравниваются ключ, значение, окружение и известная история схемы. |
| AMQP / RabbitMQ | Посмотрите на **Map**, как отправитель через обменник и правило маршрутизации связан с очередью слушателя. Незнакомая привязка остаётся поводом для проверки. |
| gRPC | Откройте `.proto` и Java/Kotlin код сервера и клиента. **Map** связывает поддержанные вызовы. **Details** показывает, например, исчезнувший метод или смену типа поля. |
| Спецификации других команд | Добавьте OpenAPI или AsyncAPI в `manifests` корневого `.archflow.yml`. После анализа в **Map** рядом с кодом будут объявленные маршруты или сообщения. |
| Браузерный клиент | Укажите фронтенд и обслуживающий его API в `.archflow.yml`. В **Map** и **Changes** ищите поддержанные обращения `fetch` или axios и формы данных TypeScript. Возможность в режиме **preview**. |
| Изменение таблицы | Добавьте миграцию Flyway или Liquibase и откройте **Changes → Details**. Плагин сопоставит старый и новый код JPA, чтобы найти сервис, который продолжит читать удалённую колонку. |
| Читатель за пределами проекта | Объявите внешнего читателя таблицы, колонки или HTTP-маршрута и причину в `.archflow.yml`. Тогда при удалении таблицы или переносе адреса **Details** сможет назвать этого читателя. |
| Кому разрешено записывать данные | Объявите в `.archflow.yml` одного владельца записи или правило «отправлять только после commit». **Problems** покажет нарушение, а **Changes** — внесла ли его правка. |
| Поведение, скрытое от теста | В Java проверьте **Problems → Notes** для внешнего вызова во время транзакции, задания без блокировки при нескольких копиях сервиса или неограниченной выдачи `findAll()`. |
| Настройки Spring как договорённость | После переименования ключа проверьте **Changes**. Там виден случай, когда код уже читает новое имя, а конфигурация ещё задаёт старое. |

## Передать результат или подготовить выпуск

Меню **More actions** можно найти на панели **Map**. Сохранение или копирование отчёта оставляет вам возможность прочитать его до отправки. [Подробности изменения](VISUAL_GUIDE_RU.md#details) · [Порядок выпуска](VISUAL_GUIDE_RU.md#rollout)

| Задача | Где получить результат |
| --- | --- |
| Коротко объяснить правку коллеге | **Changes → Summary → меню ⋯ → Copy Summary for My Team** копирует вывод, охват и затронутые сервисы. |
| Подготовить текст для ревью | **More actions → Copy or save the change review…** даёт сводку и список изменений контрактов в Markdown, а также отдельные заметки для затронутых команд. |
| Решить, какой сервис выпускать первым | В **Changes → Details → Review Options → Compare with Production** сравните с привязанной в `release.production` версией Git. В меню экспорта ревью выберите **Copy rollout plan**, чтобы прочитать предложенный порядок и шаги, которые ещё нужно проверить. |
| Проверить сериализацию на живых классах | Для поддержанной пары в подробностях выберите **Replay with real Jackson (experimental)**. Собранные классы запишут и прочитают сгенерированный образец. Увидите потерянное поле или ошибку. |
| Добавить сведения о настоящем запуске | Укажите в проекте сохранённые наблюдения о Spring-компонентах, выполненном тесте контракта, развёртывании Kafka или вызовах из трасс OTLP, Jaeger или Zipkin. При анализе видны источник, область и причина отказа, если запись устарела или конфигурация сменилась. [Учебные данные](../projects/runtime-evidence/README.md) |
| Подключить конфигурацию извне | Закрепите локальный источник параметров Config Server вместе с его происхождением. После анализа можно проследить, откуда взялись настройки и чего не получилось прочитать. |
| Сохранить машинный отчёт | **More actions → Copy or save JSON…** даёт снимок проекта или результат сравнения. **Export…** сохраняет диаграмму в Mermaid, SVG или PNG и замечания в SARIF. |
| Найти контракты для уборки | **More actions → Copy contract cleanup report** перечисляет устаревшие операции, их известных клиентов и связи без найденной второй стороны. |
| Дать другому репозиторию свой контракт | В меню JSON выберите **Publish contracts to team registry…**. Команда добавит договорённости в локальную папку командного реестра. Отправку в Git команда выполняет отдельно. |
| Проверить commit в CI | В меню экспорта ревью выберите **Copy commit trailer for this check**. **Add commit receipt check to CI…** готовит проверку записи для репозитория. Она относится к одному репозиторию и конкретному сравнению. |

## Дать задачу своему AI-помощнику

Здесь «агент» означает установленного вами помощника, например Claude Code, Codex или GitHub Copilot. Он обращается к ArchVerity через MCP и получает данные открытого проекта. Для этих команд нужен современный пакет ArchVerity, работающий клиент и включённый встроенный MCP Server IDEA. Пакет для IDEA 2024.3 поддерживает обычную проверку в плагине. Интеграция ArchVerity MCP и встроенная проверка перед commit доступны в современном пакете. [Экран Agents](VISUAL_GUIDE_RU.md#agents)

| Задача | Где получить результат |
| --- | --- |
| Подключить помощника и правила для проекта | Через **Find Action → ArchVerity: Connect AI Agent…** выберите клиента, прочитайте предлагаемые файлы и выберите, что установить. Проверьте соединение настоящим запросом к этому проекту. |
| Проверять собственный commit в IDEA | В **Connect AI Agent…** включите проверку commit в IDE. Она сверит выбранные файлы с текущим `HEAD` и сообщит, если результат нельзя подтвердить. |
| Посмотреть предыдущие проверки | Откройте **Agents → Refresh history** и выберите запись. Видны результат, база и причина, по которой проверка остановила commit. |
| Запустить новую проверку | **Agents → ⋯ → Check Current Changes** сравнит текущие файлы. **Set up commit protection** поможет настроить проверку будущих попыток commit агентом. |
| Попросить ревью проекта или изменений | Выберите **Agents → ⋯ → Review Project with Assistant…** или **Changes → Details → Code review**. Выберите область, прочитайте охват и откройте замечание в исходнике. |
| Передать ревью подключённому агенту | В **Code review → Prepare for MCP** подготовьте задачу, затем **Copy assistant request** скопирует её текст. Выберите **Cancel**, если хотите остановить это ревью. |
| Изменить способ ревью | В **Code review → Method & language** выберите язык ответа и встроенные инструкции либо собственный метод. Ранее полученные замечания сохраняют прежний текст. |
| Спросить о выбранном элементе | В карточке связи, проблемы или Spring-ключа выберите действие для помощника. Ему передаётся контекст именно выбранного элемента. |
| Изменить настройки через предпросмотр | Откройте **ArchVerity: AI Settings Assistant…**, прочитайте различия и примените выбранную настройку. **Undo last change** позволяет отменить последнее применение. |
| Посмотреть сводку пользы | В меню **Agents** выберите **Copy Value Report**. **Your Estimate…** задаёт ваши исходные оценки. Их можно отличить от фактов истории проверок. |

### Что можно попросить через MCP

Можно написать обычными словами «Кто читает этот файл?» или «Что сломается, если я уберу поле?». Имена справа позволяют проверить, какой именно инструмент вызвал помощник. [Примеры подключения и вызовов](MCP_TOUR_RU.md)

| Что попросить и что получите | Имя инструмента |
| --- | --- |
| «Что ты умеешь?» Получите список задач и условий для каждой. | `archverity_capabilities` |
| «Кто зависит от этого файла?» Увидите контракты, клиентов и доступную историю изменений. | `archverity_file_contracts` |
| «Что будет, если я сделаю эту правку?» Предложенные изменения проверятся в памяти. | `archverity_simulate_change` |
| «Можно проверить то, что уже поменялось?» Получите вывод относительно выбранной версии Git. | `archverity_check_change` |
| «Какие договорённости поменялись?» Получите список изменений и известных зависимых сервисов. | `archverity_change_impact` |
| «Какие проблемы нашлись в проекте?» Получите замечания с местами в коде. | `archverity_findings` |
| «Почему плагин это утверждает?» Получите найденные основания с путями и строками. | `archverity_contract_evidence` |
| «Что выбрано сейчас?» Получите карточку конкретного узла, связи, замечания или настройки. | `archverity_context` |
| «Где читают этот ключ Spring?» Получите объявления и явные использования в коде. | `archverity_config_usage` |
| «Нарисуй связи этого сервиса». Получите схему и её узлы с исходниками. | `archverity_architecture_diagram` |
| «Куда дальше уходит этот вызов?» Получите цепочку входящих или исходящих связей. | `archverity_trace_flow` |
| «Объясни этот путь словами». Получите описание потока и сведения, по которым можно проверить его актуальность. | `archverity_explain_flow` |
| «Как проверить правку тестом?» Получите план проверок и возможные тестовые заготовки. Запуск выполняется отдельно. | `archverity_test_plan` |
| «Как перевести Kafka на новую схему?» Получите порядок шагов для отправителя и получателя и перечень недостающих сведений. | `archverity_kafka_migration_plan` |

Откройте **Tools** и выберите нужный инструмент по названию. Они работают независимо от проверки вашего последнего изменения. [Все инструменты на одном экране](VISUAL_GUIDE_RU.md#tools)

| Инструмент | Действие → результат |
| --- | --- |

| | Выберите окружение или откройте **Settings → ArchVerity API Environments**, чтобы задать обычные переменные и значения, хранимые в PasswordSafe. **Cookies** и **History** показывают данные сеанса. |
| | Импортируйте cURL, `.http`, OpenAPI или коллекцию Postman. Составленный запрос можно скопировать или сохранить в поддержанном формате. |

| | Во вкладке **Scenarios** запустите цепочку запросов с проверками и сохранением ответов для следующего шага. Остановка на первом сбое укажет конкретный шаг. |
| | Во **WebSocket / gRPC** отправьте и получите сообщение WebSocket или вызовите gRPC по набору описаний Protobuf. Для gRPC поддержаны одиночный ответ и поток ответов сервера. [Лаборатория](../projects/api-lab/README.md) |
| [Spring config](VISUAL_GUIDE_RU.md#spring) | **Inspect Spring config** найдёт ключи, профили и места использования. Выберите ключ, чтобы перейти из настройки к коду или обратно. |

| [MyBatis SQL](VISUAL_GUIDE_RU.md#mybatis) | Вставьте строки `Preparing` и `Parameters` или выделите их и вызовите **Restore MyBatis SQL**. Получите текст с подставленными параметрами для чтения. |

## Команды для терминала и CI

Эти задачи выполняет отдельная утилита ArchVerity Tools. В установке с Python-модулем введите `python -m archflow_tools <команда> --help`, чтобы узнать требуемые файлы и параметры. Для двух команд `analyze` нужна настроенная IDEA с плагином и действующей лицензией. [Как подготовить среду](ENVIRONMENT_CHECKS_RU.md#json-cli-и-headless)

| Команда | Что получится |
| --- | --- |
| `import-openapi` / `import-asyncapi` | Прочитать документ с HTTP-маршрутами или сообщениями и сохранить контракты для анализа. |
| `import-backstage` | Прочитать объявленные компоненты и связи каталога Backstage. |
| `generate-frontend` | Подготовить типизированный клиент TypeScript и описание его зависимости от API. |
| `import-verification` | Преобразовать отчёт уже выполненной проверки и привязать его к анализируемому коду. |
| `scan-amqp` | Прочитать поддержанные настройки и объявления AMQP и получить их связи. |
| `analyze` / `analyze-impact` | Запустить анализ исходников из Git через IDEA без окна и получить снимок проекта или сравнение с выбранной базой. |
| `diff` / `git-diff` | Сравнить два готовых снимка или снимки, сохранённые в Git, и увидеть разницу. |
| `policy-merge` | Объединить правила команды с правилами проекта и получить итоговую политику. |
| `ci` / `ci-impact` | Проверить готовый отчёт по заданному порогу и вернуть код завершения для CI. |
| `registry-publish` | Добавить снимок и его версию в локальную копию реестра команды. |
| `verify-receipt` | Проверить на конкретном commit запись о выполненной проверке относительно целевой ветки. |
| `validate-manifest` | Проверить файл описания контрактов до передачи другому проекту. |
| `run-provider` | Запустить настроенного внешнего поставщика данных и получить его результат. |
